# fmddr（FileMaker DDR 解析）

FileMaker の DDR は UTF-16 の巨大な単一 XML（数十〜数百 MB）。**素の Read / Grep に
投げると context を焼き切る。必ず `fmddr.py` を通す。**

同梱スクリプト: `scripts/fmddr.py`（Python 3 標準ライブラリのみ / 追加インストール不要）

```bash
FMDDR=.claude/skills/fmddr/scripts/fmddr.py   # 以下このパスで表記
python3 $FMDDR --help
```

外部ツールの DDRparser（HORNEKS, 有償）が入っている環境ではそちらでもよい。fmddr は「DDRparser が無くても同じことができる」ことに加えて、
相互参照インデックス（`xref.json`）と未使用洗い出し（`audit`）を持つ。
スクリプト本文・レイアウトオブジェクトの出力は DDRparser の出力と実測で一致している。

## 1. 入力を見分ける

DDR 出力は「概要ファイル 1 つ + FileMaker ファイルごとの `*_fmp12.xml`」の組。

```bash
python3 $FMDDR probe -i 概要.xml            # → 種別・件数・構成ファイル一覧
python3 $FMDDR probe -i なんとか_fmp12.xml
```

**`-i` には概要ファイル（`概要*.xml` / `Summary.xml`）を渡すのが基本。**
中の `<File link="...">` を辿って本体 XML をまとめて処理する。日本語ファイル名・
`【】`・macOS の濁点表記ゆれ（NFC/NFD）も解決される。個別の `*_fmp12.xml` を直接
渡してもよい。

## 2. 展開する（基本ワークフロー）

```bash
python3 $FMDDR split -i 概要.xml -o ./split --clean
```

- `-o` 出力先（必須）
- `--clean` 前回 fmddr が生成して今回生成されなかったファイルを削除する。
  削除・リネームを差分に載せたいとき常用。**fmddr が作ったファイルしか消さない**
  （`.fmddr-manifest.json` に記録された分だけ）
- `--include-account-notes` アカウントの説明欄も出力する。**既定では伏せる**
  （説明欄にパスワードが平文で書かれている DDR が実在するため）

90 MB の DDR（スクリプト 513・レイアウト 214・フィールド 2579）で約 2〜3 秒、
メモリは一定。バックグラウンド化は不要。

### 出力構造

```
split/
├── README.md      全体サマリ（最初にこれを読む）
├── index.json     全要素の一覧（名前・ID・ファイルパス・参照先）
├── xref.json      相互参照（フィールド/スクリプト/レイアウト/TO/値一覧の逆引き）
└── <ファイル名>/
    ├── README.md            件数の内訳と調べ方
    ├── Scripts/<名前>.md    1 スクリプト 1 ファイル
    ├── BaseTables/<名前>.md フィールド一覧＋計算式・自動入力・入力値の制限
    ├── Layouts/<TO>_<名前>.md オブジェクト構成（入れ子・非表示条件・トリガ）
    ├── Relationships.md     TO 一覧とリレーション（述語・連鎖削除）
    ├── ValueLists.md        値一覧＋使用箇所
    ├── CustomFunctions.md   カスタム関数
    ├── CustomMenus.md       カスタムメニューとメニューセット
    ├── Security.md          アカウント・権限セット・拡張アクセス権
    └── FileInfo.md          ファイルオプション・外部データソース・テーマ
```

各 Markdown の先頭には**その要素の依存関係が書かれている**ので、1 ファイル読むだけで
「何を参照し、誰から参照されているか」が分かる。

```markdown
# Script: 請求書自動作成
- 呼び出すスクリプト (1): sub_請求書自動作成
- 参照レイアウト (2): 請求書自動作成設定画面, メンテ_請求書DB
- 参照フィールド (34): TOP::g_年月日, 請求書DB::請求先CD, …
- 呼び出し元スクリプト (2): OPEN, 自動発行一覧_年月移動
- 呼び出し元レイアウト（ボタン/トリガ） (1): 請求書自動作成設定画面
```

## 3. 展開後の調べ方

まず `README.md` → 次に目的に応じて。

```bash
# フィールドの使用箇所（スクリプト/レイアウト/計算式/リレーション/値一覧を横断）
python3 $FMDDR xref -d ./split --field "TOP::顧客ID"

# スクリプトの呼び出し関係（呼ぶ／呼ばれる）
python3 $FMDDR xref -d ./split --script "請求書自動作成"

# 他: --layout / --to（テーブルオカレンス）/ --table（BaseTable）/ --valuelist
#     いずれも部分一致で引ける

# 未使用の洗い出し（スクリプト・値一覧・レイアウト・TO・フィールド）
python3 $FMDDR audit -d ./split

# 素の grep も効く（1 要素 1 ファイルなので結果が読める）
grep -rl "顧客ID" split/*/Scripts/ split/*/Layouts/
grep -rn "Perform Script\|スクリプト実行" split/*/Scripts/ | head
```

`audit` の結果は**候補**であって断定ではない。メニューからの手動実行、レイアウト
メニューでの切り替え、スクリプト名を計算で組み立てる呼び出しは検出できない。

## 4. 引き継ぎ資料を作る

`handover` は split 済みの索引から**章立てされた引き継ぎ資料の骨組み**を作る。
件数・一覧・依存関係・リスク箇所は機械生成され、**解釈と説明の部分だけが
「要執筆」の枠として空いている**。その枠を埋めるのが Claude の仕事。

```bash
python3 $FMDDR split -i 概要.xml -o ./split --clean       # 先に展開しておく
python3 $FMDDR handover -d ./split -o ./handover --clean
```

- `-d` split の出力先 / `-o` 資料の出力先（**split とは別ディレクトリ**）
- `--audience` 読者を選ぶ。既定 `all`。カンマ区切り可
  - `dev` — 後任の開発者向け（1〜8, 11〜15 章）
  - `survey` — 現状調査・棚卸し（1, 9, 11, 13, 14, 15 章）
  - `client` — 顧客・発注元向け（1, 5, 6, 10, 12 章）
- `--clean` 前回生成して今回生成されなかった章を削除
- `--limit` 棚卸し章の列挙件数（既定 60）

生成される章:

| 章 | 読者 | 機械生成される事実 |
| --- | --- | --- |
| 01 システム概要 | 全 | 規模、起動アカウント/レイアウト、ファイルトリガ、大きい要素の TOP10 |
| 02 テーブル構成 | dev | 全テーブル × フィールド数・レコード数・TO 数・参照画面数・参照スクリプト数 |
| 03 リレーション | dev | ハブ TO、外部ファイル TO、連鎖削除のあるリレーション |
| 04 主要処理フロー | dev | 入口（ファイルトリガ/カスタムメニュー/レイアウトトリガ）、呼び出しツリー、共通スクリプト |
| 05 画面一覧 | dev, client | グループ別レイアウト表、帳票らしいレイアウト |
| 06 外部連携 | dev, client | 外部データソース × 使用 TO・開くスクリプト、メール/URL/インポート等のステップ検出 |
| 07 権限マトリクス | dev | **テーブル × 権限セットのマトリクス**、権限セットの設定、アカウント、拡張アクセス権 × 権限セット |
| 08 改修時の注意点 | dev | 認証情報の埋め込み検出、長大スクリプト、無効ステップ、同名要素、旧版残骸 |
| 09 棚卸し | survey | 未使用候補のチェックリスト（スクリプト/値一覧/レイアウト/TO/フィールド） |
| 10 業務仕様サマリ | client | 画面構成（掲載可否付き）、帳票、管理データ、選択肢マスタ |
| 11 ER 図 | dev, survey | Mermaid `erDiagram`（全体・島別・ハブ周辺）、テーブル一覧、リレーション定義 全件 |
| 12 画面遷移図 | dev, client | Mermaid `flowchart`（レイアウトグループ別）、帳票出力、遷移一覧 全件 |
| 13 機能一覧 | dev, survey | 固有機能の使用状況、全スクリプト × 実処理ステップ/呼び出し/参照レイアウト/固有機能 |
| 14 ビジネスルール台帳 | dev, survey | 計算フィールドの式 全文、自動入力・ルックアップ・入力値の制限・採番・集計の全件、移行時に手当てが要るフィールド |
| 15 命名規則の実態 | dev, survey | 接頭辞・接尾辞の使用率、命名と実態の食い違い、表記ゆれ、世代管理の命名 |

### 07 章（権限マトリクス）の読み方

セルは `C` 作成 / `R` 閲覧 / `U` 編集 / `D` 削除 / `-` アクセスなしの組み合わせ。
末尾の `*` は**フィールド単位の制限あり**（`FieldAccess=Limited`）。

**レコードアクセスが `Custom` の権限セットだけがテーブルごとの設定を持つ。**
それ以外（`CreateEditDelete` / `ViewOnly` など）は全テーブルに同じ設定が効くので
同じ記号が並ぶ。列が一様なのは手抜きではなく、そういう設定だという意味。

### 14 章（ビジネスルール台帳）の使い方

「この金額はどう決まるのか」をフィールド定義側から引くための台帳。**計算フィールドは
式を全文載せる**（式そのものが仕様なので）。自動入力・ルックアップ・入力値の制限は
全件を表にし、式は 1 行に丸めて元の Markdown へリンクする。

**スクリプト側に書かれたルールはこの章に出ない。** 同じ計算がフィールド定義と
スクリプトの両方にある二重管理は改修事故の典型なので、執筆枠で拾う。

### 15 章（命名規則の実態）の位置づけ

**規約を書いた資料ではなく、実際の名前を数えた結果。** 接頭辞の使用率と例外の数が
出るので「規約として採用できるか」が判断できる。`g` を含む名前とグローバル属性の
突き合わせのように、**命名と実態の食い違いを件数で示す**のが主目的。
移行時にフィールド名から属性を推測してはいけない根拠になる。

### 図（11・12 章）の読み方と限界

**ER 図** は **TO をベーステーブル単位に集約**している（TO のままだと 300 超のノードで
読めない）。多重度は結合フィールド名からの推定で、FileMaker は基数を宣言しないため
`}o--o{`（多対多）は「まだ判定できていない」の意味に近い。グラフが 1 つの島に
繋がっている場合は、関連の多いテーブルごとの**周辺図**が追加で出る。

**画面遷移図** は 2 通りの経路を拾う。

- 実線 — レイアウト上のボタン・トリガが直接切り替える
- 破線 — レイアウトが呼ぶスクリプトの中で切り替える（ラベルが経由スクリプト）

**帳票・印刷レイアウトへの切り替えは図から外し**、「帳票出力」節に分けている
（出力のための一時的な移動で、画面遷移ではないため）。図は同じ経路を 1 本に束ねるが、
**遷移一覧の表は全件を落とさず載せる**。網羅性は保証できない — スクリプトから任意の
レイアウトへ飛べるし、レイアウト名を計算で組み立てる切り替えは追えない。逆に、
スクリプトが内部で一時的に切り替えるだけの経路も拾ってしまう。

### estimate-docs との関係

`estimate-docs` skill も同じ 3 点を作るが、**目的が違う**（見積もりの母数と単価）。
`handover` 側は粒度を細かく取り、`estimate-docs` 側は見積書に載る粒度に丸める。

**ステップ名 → 固有機能の対応表、実処理ステップ数の数え方、リレーションの多重度推定は
fmddr.py が単一の出どころ**（`STEP_FEATURES` / `real_steps()` / `infer_cardinality()`）。
estimate-docs はこれを import している。**どちらかで再定義しないこと** — 2 つの skill で
数字がずれる。

### 執筆の進め方

1. `handover/README.md` を読む（目次と残り件数が出ている）
2. `grep -rn '要執筆' handover/` で枠を洗い出す
3. **枠ごとに、書かれている「手掛かり」の split 出力を読んでから書く。**
   推測で埋めない。スクリプト名・レイアウト名だけから業務を断定しない
4. 書けたら**引用ブロックごと消す**（マーカーが残っていると未完了扱い）
5. `grep -rc '要執筆' handover/` が 0 になったら完了

枠は 24 箇所（`--audience all` の場合）。1 章ずつ順に埋めるのが速い。
02 章の「各テーブルの役割」のように**表に列を足す**タイプの枠は、
表を書き直す形で埋める。

```bash
# 例: 04 章を書くために起動フローを追う
sed -n '1,40p' handover/04_主要処理フロー.md      # 呼び出しツリーを見る
head -40 split/*/Scripts/OPEN.md                  # 依存関係と本文を読む
python3 $FMDDR xref -d ./split --script "年月移動" # 呼ぶ／呼ばれるを確認
```

### 注意

- **`handover` を再実行すると加筆した本文は上書きされる。** 書き終えた資料は
  Git にコミットしてから DDR を再出力する
- 08 章は認証情報が埋め込まれている**場所**を指すだけで値は載っていない。
  **値を資料に転記しないこと**
- 「未使用」「帳票らしい」「旧版らしい」は命名やステップ名からの推測。
  断定する前に該当ファイルを確認し、資料には推測であることを残す
- 07 章と 10 章は配布範囲が違う。同じディレクトリに置いたまま顧客に渡さない
- 14 章は式を全文載せるので長い（この DDR で約 3,400 行）。通しで読ませるのではなく、grep か目次から必要な節だけ開く

## 5. 展開せずピンポイントで調べる

DDR が巨大で 1 要素しか要らないとき、または fmddr が整形していない情報
（テーマの CSS、印刷設定など）を見たいとき。

```bash
# その階層にどんな子要素・属性があるか列挙する（構造の下見）
python3 $FMDDR nodes -i X_fmp12.xml '/FMPReport/File/ScriptCatalog/*/Script'

# 特定要素の生 XML を切り出す（-o でファイル出力）
python3 $FMDDR extract -i X_fmp12.xml \
  '/FMPReport/File/ScriptCatalog/*/Script:name="検索モード"' --non-empty

# 「特定の子孫を含む要素だけ」に絞る（例: あるサブスクリプトを呼ぶスクリプトだけ）
python3 $FMDDR extract -i X_fmp12.xml \
  '/FMPReport/File/ScriptCatalog/*/Script' \
  --inner '*/Script:name="共通処理"' --non-empty
```

パス式の規則:

- `*` は**中間階層を任意個**マッチする。スクリプトはスクリプトグループの入れ子に
  なっているので、`ScriptCatalog/Script` ではなく **`ScriptCatalog/*/Script`** を使う
- 属性は末尾に `:name=検索モード` / `:name="検索モード"`。`--inner` では属性を省略可
- shell に食われるので**シングルクォートで囲む**
- `Script` / `Field` / `Layout` / `Table` などのタグは**定義と参照の両方**で使われる。
  `*` を使うとステップ内の参照（空の自己終了タグ）もヒットするので、定義だけが
  欲しいときは `--non-empty` を付ける
- 一致なしは**パス式の誤りとは限らない**。その要素がそのファイルに存在しないだけの
  ことも多い。疑う前に `nodes` で実際の構造を確認する

主要パスと DDR の構造は `reference/ddr-xml-map.md` を参照。

## 6. Git と組み合わせる

DDR を定期出力して `split` 結果をコミットすると、FileMaker の設計変更が差分で追える。

```bash
python3 $FMDDR split -i 概要.xml -o ./split --clean
git add split && git commit -m "DDR $(date +%F) 時点"
```

## 7. 注意

- **展開結果を安易に外部へ出さない。** スクリプトのコメント・アカウント一覧・
  値一覧には実在の顧客名・担当者氏名・社内アカウント名が平文で含まれる。
  外部サービスへの貼り付けや公開リポジトリへのコミットは事前に確認する
- **アカウントの説明欄にはパスワードが書かれていることがある。** 既定では伏せてある。
  必要なときだけ `--include-account-notes`
- DDR は UTF-16。`cat` すると 1 文字おきに空白が見える表示になるが破損ではない。
  **中身の確認は fmddr 経由で行う**
- SaveAsXML（`FMSaveAsXML`）形式は `split` の対象外。`nodes` / `extract` は任意の
  XML に使えるので、構造の調査はそちらで行う
- レイアウトの見た目（CSS・フォント・書式設定）は意図的に出力していない。
  必要なら `extract` で生 XML を取る
